```
                    DNS A 记录 │ (阿里云云解析, TTL 600s = 免费版下限)
        ┌──────────────────────┴──────────────────────┐
        │                                             │
   ┌────▼──────────────┐                     ┌────────▼─────────────┐
   │ home 主站 .150     │                     │ 阿里云 47.96.188.129 │
   │ nginx:8088         │                     │ nginx:80/8088        │
   │ erp-pc-web         │                     │ erp-pc-web(18080)    │
   │ erp-backend        │                     │ erp-backend(127.0.0.1:8080) │
   │ erp-mysql (主库)   │◄── 反向 SSH 隧道 ───│ erp-mysql (从库, read_only=ON) │
   │ erp-tunnel ────────┼──► aliyun:13306/12222│ erp-redis            │
   └────────────────────┘                     └──────────────────────┘
                                    erp-backend 的数据源 =
                                    SPRING_DATASOURCE_HOST=172.18.0.1:13306 (隧道)
```

- 正常态: 阿里云 `erp-mysql` 是 `.150` 的**只读从库**(`read_only=ON`, `server_id=3`), 阿里云 backend 通过隧道写 `.150`。
- 隧道由 `.150` 的 `erp-tunnel` 容器发起 (`ssh -R 172.18.0.1:13306:192.168.0.150:13306` + `:12222`), `.150` 掉线 = 隧道断 = 阿里云数据源失效。
- `.32` 飞牛是 `.150` 的另一条只读从库, **不参与接管**; 接管期间必须 `SET GLOBAL super_read_only=1` 冻住, 否则 backend 用 root 连库会绕过 `read_only` 把真实单据写进副本 (2026-10-31 已发生: 4 张销售出库在副本上重复过账)。
- **公网端口**: 用户 URL 带端口, 所以阿里云 ECS 安全组必须放行 `8088` 和 `18080` (本机 firewalld 的 18080 已 DNAT 到 8088)。只放行 80/443 时 DNS 切了用户也打不开 —— 2026-10-31 首次真实接管就是这个坑。

## 2. 状态机

状态文件: 阿里云 `/var/lib/erp-failover/state` (首行第一列)

| 状态 | 含义 | 谁会写 |
|---|---|---|
| `normal` | 主站正常, 阿里云只读从库 | 安装 / `finish` |
| `failed_over` | 阿里云已接管 (本地库可写, backend 连本地库) | `promote` |
| `restoring` | 回切进行中 (阿里云已冻结) | `freeze` |

`.150` 的守卫每 2 分钟读这个值: `failed_over` → 冻结 `.150` 写入并停 backend; `normal` 且处于冻结 → 解冻; 其他 → 不动。

## 4. 自动接管

### 4.1 触发条件
`tick` 每 30s 用**业务账号** `erp_aliyun` 经隧道连 `.150` 执行 `SELECT 1`:
- 成功 → 计数清零。
- 失败 → 计数 +1; 达 **3 次**(约 90s) 后再 `sleep 15` 复核一次, 仍失败才接管 (总计约 2 分钟, 过滤宽带抖动)。

### 4.2 接管动作 (顺序)
1. `SHOW REPLICA STATUS` 存档到 `/var/lib/erp-failover/replica-status-<ts>.txt` (记录故障瞬间延迟, 用于事后评估可能丢失的数据窗口)。
2. `STOP REPLICA` → `SET GLOBAL super_read_only=0; read_only=0`。
3. 用 `erp_failover` 建一张临时表再删 (证明业务账号真能写, 不是 root 特权假象)。
4. 改写 `/opt/erp-system/.env`: `ERP_DB_HOST=erp-mysql` / `PORT=3306` / `USER=erp_failover` / `PASSWORD=…` (首次改写前留 `.env.bak_failover`)。
5. `state=failed_over` → `docker compose up -d --no-build erp-backend`。
6. 健康判定: 容器 healthy + `http://127.0.0.1:8088/api/auth/captcha` (带 `Host: home.93gushi.com`) 200, 最多等 120s; 失败则告警要求人工介入。
7. `erp-dns-switch.sh aliyun` 把 `home.93gushi.com` 指到阿里云; 未配置 AK 时**只告警不阻断** (此时需手工改解析)。
8. 写日志 + webhook 告警(如配置)。

> **第 2 步不是可选项 (v1.1.183 实测口径)**: `SystemVersionInitializer` 是 `@Order(HIGHEST_PRECEDENCE)` 的 `ApplicationRunner`, 启动时无条件 upsert `sys_config.SYSTEM_VERSION_INFO`。v1.1.176–v1.1.182 这段代码**没有兜异常**, 在 `super_read_only=ON` 的备库上那条写必回 `ERROR 1290` → Spring 上下文启动失败 → 第 5 步的 backend 根本起不来 (2026-11-12 在 `.32` 上取证: 该站容器 `Started=2026-11-09`、`RestartCount=0`, 因为 11-10 加固只读之后从没重启过, 这颗雷一直没炸, 也导致 canary 停在 v1.1.175)。v1.1.183 起写失败只记 WARN、不再阻断启动, 但**顺序照旧**: 先解除只读再起 backend, 否则版本行写不进去、日志里会一直躺着一行 WARN。

### 4.3 接管期间
- `tick` 转为 `enforce`: 发现 MySQL 容器重启后回落 `--read-only=ON` 会**自动重新解除只读**; 数据源被改回隧道会自动改回本地; backend 掉了自动拉起。
- 主站恢复后, `tick` 检测到探测成功 → 每 30 分钟提醒一次「已恢复, 请人工回切」, **不会自动回切**。
- `.150` 守卫在 2 分钟内把主库置 `read_only=1/super_read_only=1` 并停掉 `erp-backend`, 避免两边同时写造成脑裂。

### 4.4 用户可见影响
- **需要重新登录一次**: Sa-Token 会话存在各自 Redis (`token-style: uuid`), 阿里云 Redis 没有 `.150` 的会话。App 会跳登录页。
- PC / App 的 API 地址不变 (`http://home.93gushi.com:8088/api`), 只靠 DNS 指向变化; 备用入口 `:18080` 也可用 (CORS 已含 `http://home.93gushi.com:18080`)。
- 已配 CORS 白名单: `http://home.93gushi.com:8088`、`:18080`、`http://n150.93gushi.com:8088`、阿里云 IP 各端口等。
- **DNS 生效最长约 10 分钟**: 阿里云云解析免费版 TTL 下限 600s, API 会拒绝 60s (`InvalidTTL`)。想做到 60s 需升级套餐。
- 公网端口必须在 ECS 安全组放行 `8088`/`18080`; 脚本 `entry_check` 会在切 DNS 后打**公网 IP** 自测, 不通就告警。
- 上传文件在阿里云本地目录, 由 `.150` 的 `erp-upload-pull.sh` 每 10 分钟拉回 (`--ignore-existing`)。
- 单号生成依赖 Redis 计数器 + 库内最大单号对账, 接管后不受影响。

## 5. 人工回切

前提: `.150` 已恢复 (守卫处于冻结态), 人工确认业务可以短暂停机。

```bash
# 在 .150 上, 以 root 执行
/usr/local/bin/erp-failback.sh          # 先看计划, 不加 --yes 不会执行
/usr/local/bin/erp-failback.sh --yes    # 真正回切 (停机约 1-3 分钟)
```

流程:
1. 阿里云 `freeze`: 停 backend + `read_only=1`, 状态转 `restoring` → 此后阿里云不再产生新数据。
2. 阿里云 `dump`: `mysqldump --single-transaction --databases industrial_erp | gzip` 到 `/opt/erp-system/backup/failback/`, 并写 `.meta` (sha256 + 每张表行数指纹)。
3. `.150` 用 root 反向 SSH 拉回 dump, 校验 sha256。
4. `.150` 先 `mysqldump` 备份当前库到 `data/backup/failback/pre-failback-<ts>.sql.gz`, 再用阿里云 dump **覆盖恢复** (`--databases` 自带 `DROP TABLE`), `--default-character-set=utf8mb4`。
5. **逐表行数指纹比对** (138 张表), 不一致立即中止。
6. `FLUSH BINARY LOGS` + `SHOW MASTER STATUS` 记录新主库位点。
7. `.150` 解冻 (`read_only=0`) 并启动 backend, 等 healthy + `captcha=200`。
8. 阿里云 `finish <位点>`: `STOP REPLICA` → `CHANGE REPLICATION SOURCE TO SOURCE_LOG_FILE/POS` (主机/账号/口令保持不变) → `START REPLICA` → 校验 IO/SQL=Yes → `read_only=1` → 数据源改回隧道 → 重建 backend → DNS 切回 home → `state=normal`。
9. 复核: 阿里云复制 `Seconds_Behind_Source=0`、DNS 解析到家庭 IP、`.150` 正常写。

> 为什么可以「整库覆盖」: 接管期间 `.150` 被守卫冻结 (只读 + backend 停机), 阿里云数据是 `.150` 故障点的**严格超集**, 覆盖恢复不会丢主站数据。若有人绕过守卫在 `.150` 直接写过库, 覆盖会丢这些写入 —— 所以回切前务必确认没人在 `.150` 手工改数据。

失败处理: 任一步失败脚本会告警并停止 (不会自动 finish)。 `.150` 的旧库备份在 `pre-failback-*.sql.gz`; 阿里云侧保留 dump 与 `restoring` 状态, 可用 `erp-failback.sh --yes --resume` 从恢复步骤重跑。

### 5.1 `.150` 恢复后的只读体检 (回切前, 不改数据)

`.150` 重启后 `read_only` 全局变量会回落到配置默认值, 守卫要等下一次 cron (≤2 分钟) 才会重新冻结, 而 backend 可能在 `restart: unless-stopped` 下先起来写库 → 脑裂。所以**开机后第一件事是停 backend**, 再按下面逐项看。

```bash
# ---- A. 止血 (唯一会改状态的一步) ----
/usr/local/bin/docker stop -t 30 erp-backend
ls -l /var/lib/erp-failover-guard/frozen          # 守卫冻结标记应存在

# ---- B. 机器与存储 ----
uptime; date; timedatectl | grep -E 'Time zone|synchronized'
df -h /volume3 | tail -1                          # NAS 卷挂回来了吗
ls /volume3/docker/erp-system/docker-compose.yml
dmesg -T | tail -20                               # 有没有磁盘/网卡报错

# ---- C. 容器 ----
/usr/local/bin/docker ps -a --format '{{.Names}}\t{{.Status}}\t{{.RunningFor}}'
# 关注 erp-mysql / erp-backend / erp-pc-web / erp-tunnel

# ---- D. 守卫与只读 ----
crontab -l | grep erp-failover-guard
tail -20 /var/lib/erp-failover-guard/guard.log
/usr/local/bin/docker exec -e MYSQL_PWD=***REMOVED_CREDENTIAL*** erp-mysql \
  mysql -uroot -N -B -e "SELECT @@global.read_only, @@global.super_read_only"
# 期望: 1 1

# ---- E. MySQL 完整性 ----
/usr/local/bin/docker logs erp-mysql --since 24h 2>&1 \
  | grep -iE 'ready for connections|innodb|error|corrupt' | tail -20
/usr/local/bin/docker exec -e MYSQL_PWD=***REMOVED_CREDENTIAL*** erp-mysql \
  mysql -uroot -N -B -e "SHOW MASTER STATUS; SHOW BINARY LOGS;"
/usr/local/bin/docker exec erp-mysql sh -c 'ls -l --time-style=long-iso /var/lib/mysql/*bin.0*'
# binlog 最后修改时间 = 最后写入时间; 若晚于开机时间 → 开机后被写过

# ---- F. 复制关系 ----
/usr/local/bin/docker exec -e MYSQL_PWD=***REMOVED_CREDENTIAL*** erp-mysql \
  mysql -uroot -e "SHOW REPLICA STATUS\G" | grep -E 'Source_Host|Replica_(IO|SQL)_Running|Seconds_Behind|Last_(IO_)?Error'
# 故障时必然是停的, 记录它停在哪 (后面决定是否要重定位点)

# ---- G. 反向隧道 ----
/usr/local/bin/docker logs erp-tunnel --tail 20   # 必须能连到阿里云, finish 要靠它
```

判定:

| 现象 | 结论 | 动作 |
|---|---|---|
| 容器齐、`read_only=1`、backend 已停、binlog mtime 停在故障时刻 | 标准冻结态, 无脏写 | 直接进 §5 回切 |
| `read_only=0` 或 backend 曾起来、binlog mtime 晚于开机 | 有脑裂写入 | 先 `mysqlbinlog --start-datetime` 导出这段事件评估, 人工合并后再回切 |
| MySQL 起不来 / InnoDB 报错 / 磁盘满 / `/volume3` 未挂 | 硬件或存储问题 | 先修硬件, 不要回切 |
| `erp-tunnel` 连不上阿里云 | 回切 finish 会失败 | 先恢复隧道 |

> 阿里云侧同一时间应保持 `state=failed_over`; 体检期间**不要**在 `.150` 跑 `erp-failover-guard.sh` 之外的任何写库命令。

### 6.1 首次真实接管 (2026-10-31 18:37, 非演练)

`.150` 整机失联 (同网段 `.32` 探测 22/3306/13306/18080/8088 全 closed, ping 不通), 阿里云在 18:39:56 自动 promote 成功: 停从库、本地库可写、backend 切本地 `erp-mysql`、healthy、8088 本机 200。**数据无丢失**。

暴露的两个真实问题 (已修/已入文档):
1. **DNS 未切**: AK 当时为空, 只告警未切; 补 AK 后发现云解析**免费版 TTL 下限 600s**, `ttl-low` 填 60 会被 API 拒。18:20 补齐 AK 后把记录切到 `47.96.188.129`。
2. **安全组没放行入口端口**: 当时只开 22/80/443, 公网 `8088`/`18080` 全被挡 —— DNS 切了用户也进不来。已在 ECS 安全组放行 `8088`+`18080`, 本机 firewalld 加 `18080` 并 DNAT 到 8088; 脚本新增 `entry_check` 打公网 IP 自测。
3. **`.32` 副本被别人写过**: 巡检发现 `.32` 比阿里云多 12 行 (4 张销售出库的重复过账 + 2 张重号成品入库)。原因是 backend 用 root 连副本, `read_only` 不拦 root。已 `SET GLOBAL super_read_only=1` 冻住副本; 这些重复行**不是丢失数据**, 回切时**不要**从 `.32` 回灌。

**踩到的 bug**: `finish` 用 `q()` (`mysql -N -B`) 解析 `SHOW REPLICA STATUS\G`。**批处理模式忽略 `\G`**, 输出退化成制表符横表, `Replica_IO_Running:` 匹配不到 → `io= sql=` 全空 → 误判"从库未恢复"。已修: 新增 `qv()` (不带 `-N/-B`) 专供纵向解析; 启动后单次 4s 读取改为**轮询 30s**; 新增 `finish-tail` 子命令, 复制已好时可只补收尾而不重跑 `finish` (重跑会把位点倒回 157 造成重复应用)。

### 6.3 回切后二次误接管 (2026-11-01 08:54 → 08:59, 非演练)

> 完整复盘 (时间线 / 根因分析 / 影响评估 / 处置与验证 / 改进项) 见 [`29_故障报告_20261101_两次接管事件.md`](29_故障报告_20261101_两次接管事件.md)。

回切完成约 5 分钟后, 阿里云在 08:54:47 **又自动接管了一次**, `.150` 于 08:56 被守卫冻结。整条链是三个独立问题叠加:

| 环节 | 现象 | 根因 |
|---|---|---|
| 探测失败 | 08:53:26 起连续 3 次 `主库探测失败` | `.150` 的隧道客户端在回切期间重连过, 阿里云 sshd **残留一个 CLOSE-WAIT 会话**继续监听 `172.18.0.1:13306`; 新隧道带 `ExitOnForwardFailure` 绑不上端口, 每 5s 重试全失败 → 隧道永远回不来 |
| 误接管 | 08:54:47 `promote(auto)` | 探测只剩"隧道这一条路径", 隧道断 = 看起来像主站挂 |
| 解析写错 | 回切后 `home.93gushi.com` 被写成 `115.209.189.247` (已失效) | `DNS_TARGET_HOME` 是写死的旧家庭 IP; 当时家宽实际已是 `183.152.23.59` |
| 同值报错 | `erp-dns-switch.sh home` 返回 `HTTP 400` | 阿里云对"值未变化的 UpdateDomainRecord"返回 `DomainRecordDuplicate` |

修复 (均已部署):

1. **服务端回收死会话** — 阿里云 `/etc/ssh/sshd_config` 追加 `ClientAliveInterval 15` / `ClientAliveCountMax 3`: 客户端掉线后 sshd 最长 45s 释放转发端口。
2. **探测前先自愈** — `erp-failover.sh tick` 在判定故障前跑 `heal_tunnel` (无 ESTAB 的 `sshd: erp-tunnel` 会话直接 kill), 再给 **30s 重连窗口**, 期间探测恢复就取消接管。检测时间从 ~75s 放宽到 ~135s, 只对"真·主站不可达"生效。
3. **家宽 IP 自解析** — `refresh_home_ip`: 切 DNS 前用**隧道 SSH 连接的对端 IP**(即家宽当前公网 IP) 刷新 `/var/lib/erp-failover/dns-home-ip`; `erp-dns-switch.sh home` 优先级改为 `命令行 ip > 落盘文件 > 静态 DNS_TARGET_HOME`。
4. **DNS 幂等** — 目标值与现记录相同且 TTL 相同时直接返回 `[未变更]`, 不再触发 400。

二次回切 (08:59):

| 步骤 | 结果 |
|---|---|
| 1–2 冻结 + dump | `aliyun-20261101-085907.sql.gz` |
| 3 sha256 | `a9fedf0b…` 一致 |
| 4 `.150` 自备份 | `pre-failback-20261101-085924.sql.gz` (755 KB) |
| 5–6 恢复 + 指纹 | **138 张表一致** |
| 7 新主库位点 | `mysql-bin.000006:157` |
| 9 `finish` | **通过** (io/sql=Yes), 上一条修好的解析生效 |
| 数据核对 | 这段接管期间 `sys_oper_log` 新增 **0 条**, 业务表行数与 `.150` 完全一致 → 回切无覆盖风险 |

> 经验: 家宽这条线当天公网 IP 变了三次 (`115.209.189.247` → `115.209.48.113` → `183.152.23.59`), **任何写死家庭 IP 的配置都会失效**; 唯一可靠来源是隧道连接的对端地址。另: 本机浏览器/系统 DNS 缓存 (macOS `dscacheutil`) 会比公网解析滞后, 验证时用 `curl --resolve` 绕过。

## 7. 已知限制 / 待办

1. **DNS TTL 下限 600s**: 阿里云云解析免费版不允许更低的 TTL, 切换解析最长约 10 分钟生效。AK 已配置 (`/etc/erp-dns.env`, 600, 仅 DNS 权限), 自动切换可用。
2. **ECS 安全组入口端口**: 用户 URL 带端口, 安全组必须放行 `8088`/`18080`。当前 AK **无 ECS 权限**, 改安全组仍需人工在控制台操作; `entry_check` 会在没放行时告警。
3. **会话不迁移**: 接管后必须重新登录 (各站 Redis 独立)。如不能接受, 需把 Sa-Token 改为无状态 JWT 或做会话同步。
4. **`.32` 飞牛不参与**: 接管期间必须 `super_read_only=1`; 它以 `.150` 为源会停在故障点。**2026-11-01 回切后实测: 不需要整库 resync** —— 它的复制源一直是 `.150` (故障期间 `.150` 只是外部不可达, 库还活着), 解冻后已自动追到 `mysql-bin.000006`, `IO/SQL=Yes`、`Seconds_Behind_Source=0`、138 表行数与 `.150` 一致、`prd_finished_in` 无重复单号。处置只需 `SET GLOBAL super_read_only=0; SET GLOBAL read_only=1` (容器启动参数 `--read-only=ON` 的常态), backend 保持 healthy 即可。若将来 `.32` 复制中断过且有人往里写过, 才退回"用 `.150` dump 覆盖导入再按新位点重建复制"。
5. **MySQL 容器重启会回落只读**: compose 里有 `--read-only=ON`, 接管态靠 `tick/enforce` 每 30s 纠正, 极端情况下最多 30s 写失败。
6. **回切是覆盖式恢复**: 前提是 `.150` 接管期间没有写入; 回切期间停机 1-3 分钟。
7. **故障瞬间延迟即丢数窗口**: `promote` 会把 `Seconds_Behind_Source` 记录在 state 目录, 接管告警里也带这个数值。
8. **家庭 DDNS 与公网 IP 变动**: 宽带重播后路由器 DDNS 会把 `home.93gushi.com` 自动改回新家庭 IP (对回切是好事, 不用手工切)。但 2026-11-01 一天变了三次 IP, **写死家庭 IP 的配置一定会失效** —— `DNS_TARGET_HOME` 现在只是兜底, 实际值由 `refresh_home_ip` 从隧道连接对端实时取。接管期间若只是 NAS 坏、路由器仍在, 要确认 DDNS 不会把解析从阿里云改回去。
9. **隧道是单点**: 阿里云到 `.150` 只有反向 SSH 隧道这一条路, 隧道断时探测也断。`heal_tunnel` + 服务端 `ClientAliveInterval` 已能让死会话在 ~45s 内自动回收, 但**排查时先看隧道会话再判断主站死活**: `ssh root@47.96.188.129 "ss -ltnp | grep -E ':(13306|12222)'"`。

## 8. 常用命令

```bash
# 阿里云
/usr/local/bin/erp-failover.sh status       # 状态 / 探测 / 只读 / 数据源 / 健康 / 8088

tail -50 /var/lib/erp-failover/failover.log

# .150

tail -f /var/lib/erp-failover-guard/failback-*.log
```
