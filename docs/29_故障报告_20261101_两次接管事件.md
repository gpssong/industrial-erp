## 1. 摘要

2026-10-31 18:37 起 `.150` 家庭宽带断线, 公网不可达约 14 小时。阿里云待命站在 18:39:56 自动接管, 期间系统对外持续可用 (补齐了 DNS AK 与 ECS 安全组入口端口)。

2026-11-01 08:22 家宽恢复, 08:44:59 完成首次人工回切 (138 张表指纹一致)。**回切约 5 分钟后, 阿里云在 08:54:47 又自动接管了一次**, `.150` 于 08:56 被守卫冻结, 08:59:07 经二次回切恢复正常。

二次接管不是"主站真的又挂了", 而是三个独立缺陷叠加:

| # | 缺陷 | 直接后果 |
|---|---|---|
| 1 | 阿里云 sshd 残留 CLOSE-WAIT 会话, 继续占着反向隧道的 `172.18.0.1:13306` | `.150` 新隧道 `ExitOnForwardFailure` 绑不上端口, 每 5s 重试全失败 → 隧道永远回不来 |
| 2 | 探测只有"经隧道访问 `.150`"一条路径 | 隧道断 = 看起来像主站挂 → 连续 3 次失败后 promote |
| 3 | `DNS_TARGET_HOME` 写死旧家庭 IP (`115.209.189.247`) | 回切把解析写到一个已失效地址; 且同值更新触发阿里云 `DomainRecordDuplicate` (HTTP 400) |

**影响**: 二次接管窗口内无任何业务写入 (`sys_oper_log` 新增 0 条, 138 表行数与 `.150` 完全一致), 二次回切为安全覆盖, **无数据丢失、无重复单据**。

**修复**: 服务端 SSH 会话回收 (≤45s) + 探测前自愈隧道并给 30s 重连窗口 + 家宽 IP 从隧道对端实时自解析 + DNS 更新幂等 + `finish` 纵向解析修正。全部已部署并验证。

## 4. 根因分析

### 4.1 主链: 死隧道会话 → 探测失败 → 误接管

1. 首次回切过程中 `.150` 的隧道客户端重连过一次, 阿里云 sshd **没有回收旧会话** —— 该会话的 TCP 已进入 `CLOSE-WAIT`, 但 sshd 仍持有反向转发监听 `172.18.0.1:13306`。
2. `.150` 新隧道带 `ExitOnForwardFailure=yes`, 绑不上已占用端口 → 每 5s 重试, 全部失败 → 隧道永远回不来。
   - 客户端 `ServerAliveInterval=30 / CountMax=3` 对**服务端残留的会话**无效, 只有服务端 `ClientAlive*` 能回收。
3. 阿里云 `probe_primary` 的唯一路径是"经隧道连 `.150` MySQL"。隧道断 → 探测必失败, 与"`.150` 真挂"不可区分。
4. 失败计数达 3 次 + 15s 复核后 `promote(auto)`, 于 08:54:47 接管; `.150` 守卫 2 分钟后读到 `failed_over` 冻结。

### 4.2 并发缺陷: 解析写死 + API 非幂等

- `refresh` 之前 `DNS_TARGET_HOME` 是静态旧地址 `115.209.189.247` (`/etc/erp-dns.env`)。当天家宽公网 IP 变了三次 (`115.209.189.247` → `115.209.48.113` → `183.152.23.59`), 静态值必然过期。
- 首次回切后 `erp-dns-switch.sh home` 把 A 记录写成已失效地址, 返回 **HTTP 400 `DomainRecordDuplicate`** —— 阿里云对"值未变化的 UpdateDomainRecord"报错, 脚本因此中断, 需人工兜底。

### 4.3 首次回切的误报 (非故障, 但干扰判断)

`finish` 用 `q()` (`mysql -uroot -N -B`) 解析 `SHOW REPLICA STATUS\G`。**批处理模式忽略 `\G`**, 输出退化成制表符横表, `Replica_IO_Running:` 匹配不到 → `io=` / `sql=` 全空 → 误判"从库未恢复"。实际复制已 `IO/SQL=Yes`。

### 4.4 为什么监控没有提前拦下

- 探测只有单路径, 没有"主站是否真的不可达"的第二证据 (例如 `.150` 的公网端口/独立健康端点)。
- 判定阈值只看"失败次数", 不看"失败原因是否集中在隧道/端口占用"。
- 接管成功后只发 webhook 告警, 没有"接管后 N 分钟无人确认则升级"的强制流程; 二次接管靠人工巡检发现。

## 5. 处置过程

### 5.1 首次接管期间 (10-31 18:39 → 11-01 08:22)

系统由阿里云对外服务。期间修补环境: DNS AccessKey 与 TTL 600、ECS 安全组放行 `8088`/`18080`、`.32` 强制 `super_read_only=1` 防脑裂写入。

### 5.2 首次回切 (11-01 08:44:59)

先做只读体检 (不改数据): `sys_oper_log` 在故障后 **0 条**; 138 表行数比对仅 `sys_login_log` 差 4 行 (阿里云侧登录); 全库 `CHECKSUM TABLE` 4 处差异全部可解释; `.150` binlog mtime = 当日 03:00 定时备份。判定无脏写后执行: 冻结 → dump → sha256 → `.150` 自备份 → 覆盖导入 → 138 表指纹 → 解冻 + backend → 阿里云重建复制。`finish` 因 §4.3 的解析 bug 误报, 实际复制已恢复。

### 5.3 二次误接管识别与止血 (08:54:47 → 08:59)

发现 `state=failed_over` 后:

1. `ss -ltnp | grep 13306` / `ss -tnp` 看到 `CLOSE-WAIT` 的 `sshd: erp-tunnel` 会话仍占 `172.18.0.1:13306`;
2. `ps -eo pid,args | grep 'sshd: erp-tunnel'` 定位 pid 并 kill;
3. `.150` 隧道 5s 内重连, 探测恢复;
4. 核查二次接管期间无写入 (`sys_oper_log` 新增 0 条, 138 表行数一致), 确认覆盖式回切安全。

### 5.4 二次回切 (08:59:07)

流程同首次, 结果: dump sha256 `a9fedf0b…` 一致, **138 表一致**, 新位点 `mysql-bin.000006:157`, `finish` **通过** (io/sql=Yes)。随后修正 DNS 解析到 `183.152.23.59`。

### 5.5 `.32` 恢复 (09:1x)

判定**不需要整库 resync**: 它的复制源一直是 `.150` (故障期间 `.150` 只是公网不可达, 库仍活着), 未写过脏数据。处置: `SET GLOBAL super_read_only=0; SET GLOBAL read_only=1` (与容器 `--read-only=ON` 的常态一致), backend 保持 healthy。验证: 复制 `IO/SQL=Yes`、`Seconds_Behind_Source=0`、`mysql-bin.000006:2019`、138 表行数与 `.150` 一致、`prd_finished_in` 无重复单号、`8080` healthy、`captcha=200`、`18080=200`。

## 8. 经验教训

1. **探测路径单一 = 把依赖故障等同于主站故障。** 判定"主站死活"至少要有两条互相独立的证据链; 隧道、DNS、安全组任何一环都不能单独作为判据。
2. **长连接隧道类故障, 客户端 keepalive 不够。** 客户端断了不一定通知服务端, 必须服务端设 `ClientAliveInterval`/`ClientAliveCountMax` 主动回收, 否则死会话会一直占着转发端口, 把"能恢复"变成"永远恢复不了"。
3. **随时间/环境变化的配置必须运行时推导。** 家宽一天变三次 IP, 任何写死的家庭 IP 都会在关键时刻指向死地址; 隧道连接的对端地址才是唯一可靠来源。
4. **自动切换动作必须幂等。** DNS 同值更新返回 400 就把回切卡住, 说明"检查 → 更新"没有做状态判断; 复制重建、覆盖导入同理, 重跑不能把位点倒回。
5. **覆盖式回切的前提必须先用证据证明, 不能靠"应该没人写"。** 三层证据: `sys_oper_log` 时间线、138 表行数、全库 `CHECKSUM TABLE`, 再看 binlog mtime 是否只是定时备份。
6. **一次回切完成 ≠ 系统稳定。** 本次二次接管发生在首次回切后 5 分钟, 恰好是"以为收工"的时段; 回切后必须留观察期, 且要检查隧道会话而不是只看 state。
7. **批处理模式的 MySQL 客户端会忽略 `\G`。** 纵向解析一律用不带 `-N/-B` 的客户端调用, 否则把"复制正常"读成"复制没起来"。
8. **副本恢复要按证据判断是否需要 resync。** `.32` 复制源一直是 `.150`、且无人往副本写过, 就不需要整库覆盖; 盲目 resync 反而可能撞 `1062`。
